# PASEO 비교: Ropeman 추출과 Graphify `graph.json`을 같은 모델·프롬프트에 넣기

> 측정일 2026-11-13. 대상 PASEO 커밋 `e0f545fed`. 다시 돌리는 법은 끝의 "다시 돌리기"에 있다.
> Graphify는 Graphify Labs의 프로젝트이며 Ropeman은 Graphify와 관련이 없다. 여기서는 Graphify가 만든 `graph.json` 형식만 읽는다.

## 1. 무엇을 정하려는가

`graph.json`(Graphify가 저장소를 읽어 만드는 그래프 파일)을 Ropeman의 **주 입력**으로 쓸지, Ropeman 자체 추출을 주 입력으로 두고 `graph.json`은 **보조 입력**(선택해서 여는 어댑터 하나)으로 둘지를 정한다. 이 결정은 `graph.json` 입력 규칙(ast 층과 외부 노드만 읽고 LLM이 만든 semantic 층은 계층 입력에서 뺀다)의 마지막 미정 항목이다.

방법은 한 가지 변수만 바꾸는 실험이다. 같은 모델, 같은 프롬프트, 같은 폴더에 입력만 두 가지로 넣는다.

- **ropeman**: `packages/core`의 `extractDirectory`(파일 수 상한 없는 Node 추출)가 만든 코드 지도
- **graphify**: Graphify 0.9.104가 만든 `graph.json`을 `graphifyAdapter.ts`로 읽은 코드 지도

두 입력 모두 같은 타입(`CodeMap`)이 되고, 같은 함수(`folderView` → `renderPrompt`)가 프롬프트로 바꾼다. 그래서 프롬프트의 차이는 지도 내용의 차이뿐이다.

## 2. 사전 등록 (모델 호출 전에 적음)

2-1부터 2-6까지는 첫 모델 호출(2026-11-12T15:38:01Z) 8초 전인 15:37:53Z에 파일로 썼다. 이 저장소만으로는 이 순서를 확인할 수 없다. 근거와 그 한계는 3-7에 있다.

(2026-11-13 리뷰 뒤 고침) 처음에는 "각 실행 기록(`runs/*.json`)에는 호출 시각이 남는다"고 적었지만, 이번 실행 기록에는 시각이 없었다. 지금 스크립트는 호출마다 시작 시각(`calledAt`)과 이 절의 SHA-256(`preregistration.sha256`)을 실행 기록에 남기고, `--prereg`로 이 문서를 받지 않으면 모델을 부르지 않는다. 그래서 다음 실행부터는 실행 기록의 해시를 git 이력의 이 절과 맞춰 볼 수 있다.

### 2-1. 입력 준비

- PASEO를 직접 건드리지 않으려고 `git archive HEAD`로 복사본을 만들고 두 추출을 모두 그 복사본에서 돌린다.
- PASEO에 이미 있던 `graphify-out/graph.json`은 `packages/server`만 담고 있었다(코드 파일 1,305개, `.tsx` 0개). 저장소 전체를 비교하려고 복사본에서 `graphify update --no-cluster`(LLM 없음)와 `graphify cluster-only --no-label --no-viz`(군집만, 이름 붙이기 LLM 없음)로 새로 만들었다. `--no-cluster` 출력에는 `graph.schema_version`이 없어 어댑터가 거부하므로 두 번째 명령이 필요하다.
- Ropeman 추출은 복사본 안에 생긴 `graphify-out/`을 건너뛴다(빌드 산출물이라 저장소 내용이 아니다).

### 2-2. 모델에게 시키는 일

한 폴더의 "부분"(바로 아래 하위 폴더와 그 폴더에 바로 있는 파일)을 역할별 묶음으로 나누고 이름을 붙인다. 프롬프트에 들어가는 것은 결정론 추출 결과뿐이다.

- 부분마다: 경로, 파일 수, 심볼 수, 큰 파일부터 고른 최상위 클래스·함수 이름 최대 6개
- 부분 사이 관계: 종류(`imports`, `calls`, `references` 등), 개수, 근거 위치 최대 3개(`{path, line, to}`). EXTRACTED이고 대상이 파일 하나로 정해진 관계만 넣는다.
- 모델은 JSON으로 답한다: 묶음마다 이름(4단어 이하), 한 문장 요약, 구성 부분, 입력에서 그대로 옮긴 근거 위치 최대 3개.

파일 원문은 한 줄도 넣지 않는다. 경로, 개수, 심볼 이름, 줄 번호만 들어간다. 실제 값이 든 `.env` 경로가 부분 목록에 있으면 스크립트가 멈춘다.

### 2-3. 대상 폴더 (고른 규칙)

1. 저장소 루트
2. `packages` (모노레포의 패키지 목록)
3. `packages/server/src`
4. `packages/app/src` 아래에서 프롬프트가 두 조건 모두 6만 자 이하인 폴더 중 파일이 많은 두 개: `packages/app/src/hooks`, `packages/app/src/screens`. `packages/app/src` 자체는 graphify 쪽 프롬프트가 56만 자라서 뺐다.

### 2-4. 모델과 호출 조건

- 로컬 `claude -p` CLI(구독), 모델 `claude-sonnet-5-5`, `--effort medium` 고정
- 도구 없음(`--tools ""`), 설정 파일·MCP 없음, 시스템 프롬프트는 "You answer with JSON only." 한 줄, 빈 작업 폴더
- CLI가 온도(temperature)와 시드를 받지 않아서 고정하지 못한다. 그래서 조건마다 3번씩 돌려 실행 간 차이를 잰다.
- 조건을 번갈아 부른다(API가 느린 구간이 한쪽에만 몰리지 않게).
- 예산: 호출 30번(5폴더 × 2조건 × 3회), 입력 토큰 40만 이하, 정가 기준 5달러 이하. 스크립트의 `--max-calls`가 호출 수를 막는다.

### 2-6. 판정 규칙

`graph.json`을 주 입력으로 올리려면 아래가 모두 성립해야 한다. 하나라도 아니면 보조 입력으로 둔다.

1. graphify 조건의 구조 검사 통과율이 ropeman 조건 이상이다.
2. graphify 입력의 디스크 확인 일치율이 ropeman 이상이다.
3. 입력이 결과를 바꾼다: 조건 간 ARI 평균이 두 조건의 실행 간 ARI 평균 중 낮은 쪽보다 0.1 넘게 낮다. 바꾸지 않는다면 입력을 바꿀 이유가 없다.
4. 3이 성립할 때, graphify 쪽 묶음이 근거를 더 많이 단다(근거를 단 묶음 비율이 더 높다).

토큰과 추출 시간은 판정에 넣지 않고 비용으로 따로 적는다.

### 3-1. 결론

**`graph.json`은 보조 입력으로 둔다. 주 입력은 Ropeman 자체 추출이다.** 판정 규칙 네 개 중 두 개가 성립하지 않는다. 결정을 가른 것은 규칙 3이고, 그 결과는 "입력을 바꿔도 묶음이 달라진다는 증거를 n=3에서 찾지 못했다"이다. 입력이 결과를 바꾸지 않는다는 뜻은 아니다.

| 규칙                      | 결과                                                                                                                                                   | 성립                               |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------- |
| 1. 구조 검사 통과율       | 두 조건 모두 15/15                                                                                                                                     | 성립 (같음)                        |
| 2. 디스크 확인 일치율     | ropeman 300/300(100%), graphify 577/600(96.2%). 어긋난 23개는 모두 검사 규칙이 줄 하나만 보는 탓으로 설명된다                                          | 성립 안 함 (약한 신호, 3-2의 주의) |
| 3. 입력이 결과를 바꾸는가 | 적은 규칙대로 재면 5개 폴더 중 루트 하나만 기준을 넘는다. 두 ARI를 같은 부분 위에서 재면 넘는 폴더가 없다(3-3). 어느 쪽이든 n=3에서 차이를 찾지 못했다 | 성립 안 함                         |
| 4. 근거를 단 묶음 비율    | 규칙 3이 성립하지 않아 판정에 쓰지 않는다                                                                                                              | 해당 없음                          |

같은 폴더를 같은 모델이 나눌 때, 입력을 바꾼 두 실행의 일치(조건 간 ARI)는 같은 입력으로 다시 돌린 두 실행의 일치(실행 간 ARI)와 같은 범위에 있다. 공통 부분 기준(3-3의 두 번째 표)으로 다섯 폴더 모두 조건 간 9쌍의 최솟값~최댓값이 실행 간 쌍의 범위와 겹친다. graphify 입력에는 호출·타입 참조 관계가 더 들어가지만, 3회씩 돌린 이 실험으로는 묶음이 달라졌다고 말할 수 없다. 대신 프롬프트는 1.2~2.4배 커졌다.

(2026-11-13 리뷰 뒤 고침) 처음에는 "루트의 차이는 호출 관계가 아니라 문서 파일 유무에서 온다"고 적었다. 같은 12개 공통 부분 위에서 재면 Ropeman 입력의 실행 간 ARI가 0.56으로 떨어져 루트의 차이도 사라진다. 처음 숫자는 실행 간 ARI를 26개 부분 전체(문서 묶음은 매번 같게 나온다)에서, 조건 간 ARI를 12개 공통 부분에서 재서 생긴 차이였다.

- 두 지도의 일치: 둘 다 읽은 파일 5,455개. Ropeman만 읽은 파일은 Markdown 239, YAML 30, Dockerfile·TOML 각 2, 템플릿 `.env` 1, JSON 1개다. Graphify만 읽은 파일은 TypeScript 76, JavaScript 14, YAML 10, 기타 19, TSX 5, Kotlin 4, JSON 4, Bash 1개다. 같은 줄에서 같은 파일을 가리키는 import는 17,384개, Ropeman에만 있는 것 277개, Graphify에만 있는 것 641개다. 차이의 원인은 조사하지 않았다.

- **디스크 확인의 주의.** Graphify 참조가 일치하지 않은 23개를 모두 원문과 대조했다(2026-11-13 리뷰 뒤 추가, 처음에는 5개만 열었다). 스크립트로 인용한 줄 아래 14줄까지 대상 이름을 찾고, 찾지 못한 것은 직접 열었다. 22개는 여러 줄에 걸친 선언의 첫 줄을 위치로 적은 경우다. 예를 들어 메서드 `receiveWorkspaceDelta`의 시작 줄을 적어서, 인자 타입 `WorkspaceDirectoryDelta`는 2줄 아래에 있었다. 22개 모두 대상 이름이 1~4줄 아래에 있다. 남은 1개는 `isSameDaemonInstance` 호출의 대상을 `isSamePidLock`으로 적은 경우인데, `daemon-instance.ts`가 `isSamePidLock`을 `isSameDaemonInstance`라는 이름으로 다시 내보내므로 Graphify가 맞다. 23개 중 관계가 틀렸다고 볼 것은 없었다. 그러니 96.2%는 이 검사 규칙이 줄 하나만 보는 탓에 생긴 숫자다. 게다가 Ropeman 쪽은 대상이 정해진 참조가 없어 import 300개만 검사했다. import만 놓고 보면 두 입력 모두 300/300이다. 규칙 2는 적은 대로 "성립 안 함"으로 두지만 약한 신호이고, 결론은 규칙 3에 기댄다.

### 3-4. 비용

- 호출 30번, 입력 토큰 336,182개, 출력 토큰 58,170개. CLI가 보고한 정가 환산 1.14달러(구독으로 냈다). 예산(호출 30, 입력 40만, 5달러) 안이다.
- 같은 폴더에서 graphify 프롬프트가 ropeman보다 1.24배(루트)~2.42배(`packages`) 크다. 늘어난 만큼은 호출·참조 관계와 그 근거다.
- CLI는 호출마다 작은 Haiku 보조 호출을 한 번 더 한다(`modelUsage`에 `claude-haiku-5-5`). 위 토큰 수는 Sonnet 호출만이고, 달러 금액에는 보조 호출이 들어 있다.

### 3-5. 하지 않은 것과 한계

- 모델 하나(`claude-sonnet-5-5`)만 썼다. `gemini` CLI로 같은 실험을 하지 않았다.
- Graphify 빌드 시간과 메모리는 한 번만 쟀다.
- 이름의 질은 사람도 모델도 채점하지 않았다. 표로 나란히 둘 뿐이다.
- 조건마다 3회라 실행 간 ARI는 쌍 3개의 평균이다. 분산을 추정할 표본이 아니어서 "차이가 없다"고 말할 수 없고 "n=3에서 차이를 찾지 못했다"까지만 말한다.
- 폴더 단위로 묶고 이름 붙이는 일만 쟀다. 호출 관계가 더 쓸모 있을 일(파일 안 드릴다운, LLM이 그린 관계를 코드 근거로 확인하는 T1-8)은 재지 않았다.
- Ropeman 호출 위치는 아직 대상을 해석하지 않는다(`pending`). 그래서 이 실험의 ropeman 조건에는 호출 관계가 아예 없다. Ropeman이 호출 대상을 해석하게 되면 결과가 바뀔 수 있다.

### 3-6. 권장

(2026-11-13 리뷰 뒤 고침) 결론은 처음과 같다. 근거를 실제로 잰 것만 남기고 다시 적는다.

1. Ropeman 자체 추출을 주 입력으로 둔다. 바꿀 이유는 측정되지 않았고, 바꾸지 않을 이유는 속도와 크기와 커버리지다.
   - 규칙 3. 폴더를 묶고 이름 붙이는 일에서, 입력을 `graph.json`으로 바꿔 묶음이 달라진다는 증거를 n=3에서 찾지 못했다.
   - 속도. 지도를 만드는 데 Ropeman은 7.2초, Graphify는 147.8초(1회 측정)로 약 20배 차이다.
   - 크기. 같은 폴더에서 graphify 프롬프트가 1.24~2.42배 크다. 묶음이 달라졌다는 증거 없이 토큰만 는다.
   - 커버리지. Ropeman은 Markdown 239개와 YAML·Dockerfile·TOML 같은 설정 파일을 담아서 루트에 문서 묶음이 생긴다. 다만 한쪽으로만 기울지는 않는다. Graphify는 Ropeman이 읽지 않은 파일 133개(TypeScript 76개, JavaScript 14개 포함)를 담았고, 이 차이의 원인은 조사하지 않았다.
2. `graph.json`은 지금 규칙(ast 층과 외부 노드, semantic 층 제외)대로 보조 입력으로 둔다. Ropeman에 아직 없는 호출·타입 참조 관계(EXTRACTED 2만 개 남짓)를 줄 수 있다.
3. 보조 입력으로 열 때는 범위를 보여 준다. PASEO의 기존 `graph.json`처럼 저장소 일부만 담은 파일이 있다.
4. 이 실험은 호출 관계가 필요한 일을 재지 않았다. LLM이 그린 관계를 코드 근거로 확인하는 T1-8과 파일 안 드릴다운이 그렇다. 이번 ropeman 조건에는 호출 관계가 하나도 없었으므로, 그 일을 시작하기 전에 Ropeman 호출 해석과 `graph.json` 호출 관계를 그 일 기준으로 다시 재고 판단한다. 그 측정에서 `graph.json`이 낫다면 이 결론은 바뀔 수 있다.

### 3-7. 사전 등록과 재현을 어디까지 확인할 수 있나 (2026-11-13 리뷰 뒤 추가)

확인할 수 있는 것:

- 2절의 사전 등록 문장. 작성 세션의 로컬 기록(Claude Code 세션 로그)에 이 문서를 15:37:53Z에 처음 쓴 내용이 남아 있다. 그 내용에 Prettier 서식을 적용하면 커밋된 1~2절과 바이트 단위로 같다. 첫 호출은 15:38:01Z였다. 다만 이 기록은 작성자의 컴퓨터에만 있어서 저장소를 받은 사람은 확인할 수 없다. git에는 문서와 스크립트가 결과와 함께 한 커밋(15:48Z)으로 들어갔다.
- 첫 호출 뒤에 바뀐 코드. 같은 세션 기록에 따르면 15:38:44Z에 `prettier --write`가 `scripts/paseo-comparison/`의 서식을 정리했다. `checks.ts`와 `inputs.ts`의 수정 시각이 15:38:45Z인 것이 이 때문이다. 15:40:32Z에는 `experiment.ts`가 실행 기록을 임시 파일에 쓰고 이름을 바꾸도록 고쳐졌다. 이 밖에 바뀐 것은 테스트 파일, `vitest.config.ts`, `run.mjs`의 변수 초기값 하나다. 실행 중인 프로세스는 시작할 때 모듈을 모두 읽었으므로 30번 호출과 요약은 바뀌기 전 코드로 돌았다. 서식 변경과 쓰기 방식 변경은 프롬프트, 검사, 요약의 값을 바꾸지 않는다.
- 위 판단을 숫자로 확인했다. 리뷰 뒤의 최종 코드로 같은 PASEO 복사본에서 모델 호출 없이(`--max-calls 0`, 기록된 30개 실행 파일 재사용) 다시 돌렸다. 프롬프트 10개는 보낸 것과 바이트 단위로 같았다. 입력 지표와 두 지도의 일치는 추출 시간을 빼고 같았다. 디스크 확인은 이제 어긋난 위치를 모두 남기는데(`mismatches`), 그 앞 5개는 처음 기록한 예시 5개와 같다. 저장된 답 30개를 최종 검사 함수로 다시 검사한 결과는 저장된 검사와 모두 같았다(`staleChecks` 0). 요약의 모든 셀, 실행 간·조건 간 ARI, 토큰·비용 합계도 같았다. 이 문서에서 바뀐 숫자는 반올림 두 군데(3-3 `hooks` ropeman 0.57→0.56, `screens` ropeman 0.62→0.61과 평균 0.69→0.68)와 새로 더한 같은 부분 기준 표뿐이다.

확인할 수 없는 것:

- 이번 30개 실행 기록에는 호출 시각과 사전 등록 해시가 없다. 호출 시각은 진행 로그와 실행 파일의 수정 시각(15:38:19Z~15:44:05Z)으로만 알 수 있고, 이것은 사후에 바뀔 수 있는 값이다.
- 처음 쓴 사전 등록에 "각 실행 기록에는 호출 시각이 남는다"는 틀린 문장이 있었다. 2절에서 고쳤다.

다음 실행부터는 실행 기록마다 `calledAt`과 `preregistration.sha256`이 남는다. 해시는 `--prereg`로 받은 Markdown 파일의 "사전 등록" 절(그 `## ` 제목부터 다음 `## ` 제목 전까지)의 SHA-256이다. 확인하는 사람은 호출 시각 이전 커밋의 이 절을 같은 방식으로 해시해서 맞춰 보면 된다.

```sh
  --folder packages/app/src/hooks --folder packages/app/src/screens
```

`--max-calls`의 기본값은 24라서 30번을 부르려면 이렇게 적어야 한다. 실행 파일이 모두 있으면 호출은 0번이고, 저장된 답을 지금 코드로 다시 검사해 `summary.json`을 새로 쓴다. 이 두 명령이 호출 제한과 `--prereg` 검사를 통과하는지는 `comparison.test.ts`가 이 문서를 읽어 확인한다.

`<out>`에 `inputs.json`(입력 지표), `prompts/`(보낸 프롬프트 그대로), `runs/`(호출마다 답과 검사 결과), `summary.json`(위 표의 숫자, `agreement.*.onCommonParts`가 같은 부분 기준 표)이 생긴다. 검사 함수의 테스트는 `scripts/paseo-comparison/comparison.test.ts`다.
