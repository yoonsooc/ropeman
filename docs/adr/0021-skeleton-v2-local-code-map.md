# ADR-21: 스켈레톤 v2는 브라우저에 두는 코드 지도로, AI 전송 형식은 v1에 고정

- **날짜**: 2026-11-12
- **문제**: 코드 지도에 줄 번호, 호출 관계, 파일로 연결된 import, 관계마다 출처(EXTRACTED/INFERRED)를 넣어야 한다. 그래야 사람과 에이전트가 관계마다 근거를 확인할 수 있다. 그런데 지금은 한 타입(`SkeletonFile`)이 파서 요약이면서 AI에 보내는 요청이다. 사실을 하나 더할 때마다 요청이 커진다. 250KB 예산에 PASEO는 이미 65~86개 파일만 들어간다. 분석 캐시 키는 요청 문자열의 SHA-256이라서, 요청이 1바이트만 달라져도 모든 사용자의 캐시가 무효가 된다.
- **검토 대안**:
  - (A) v1 전송 형식을 넓힌다. `SkeletonSymbol`에 `lines`, `SkeletonFile`에 `calls`와 `resolved`를 선택 필드로 두고, 비어 있으면 생략해 바이트를 유지한다. 지금 바꿀 양은 가장 적다. 하지만 T1-5가 호출을 채우는 순간 캐시 키가 모두 바뀌고 예산이 줄어든다. 출처를 둘 곳도 전송 필드밖에 없다.
  - (B) graphify처럼 평면 노드·관계 그래프로 바꾼다. T1-10 입력과 거의 1:1이다. 하지만 관계마다 `confidence`와 `source`를 따로 저장하면 "파서가 추론했다" 같은 잘못된 조합도 저장된다. 전송 형식을 만들려면 `contains` 관계에서 심볼 트리와 순서를 다시 짜야 해서 바이트 유지가 깨지기 쉽다. 파일 단위로 읽을 때마다 색인도 따로 필요하다.
  - (C) 파일마다 기록을 두는 코드 지도를 브라우저에만 두고, 전송 형식은 v1에서 투영한다. 관계는 그 관계가 적힌 파일의 기록에 둔다.
  - 관계를 담는 모양은 따로 네 가지를 비교했다(타입 스케치 4개, 2026-11-12).
    - (C1) 위치(site)마다 대상 후보 목록을 둔다. 호출 하나에 후보가 셋이면 위치 하나에 후보 셋이다.
    - (C2) 후보마다 관계 하나를 두고, 관계가 위치 목록의 번호를 가리킨다. graphify와 같은 모양이다.
    - (C3) 위치 목록과, 위치 id로 찾는 결과 표를 따로 둔다.
    - (C4) C1과 같지만 import 재수출을 `imports` 목록 안에 종류로 표시한다.
- **결정**: C, 관계는 C1 모양이다.
  - `types/codeMap.ts`의 `CodeMap`은 파일 기록(`FileRecord`)을 경로로 찾는 표다. 파일 기록에는 파일 전체 줄 범위, 심볼 트리(id, 모든 종류, 줄 범위), import 위치, 재수출 위치, 참조 위치가 있다. 심볼이 없는 파일도 파일 줄 범위를 근거로 쓴다(graphify의 파일 노드 `L1`).
  - 위치는 코드에 적힌 사실이다. 파서가 쓰고, 해석기는 위치의 대상(`Binding`)만 바꾼다. 대상은 `pending`(아직 아무도 안 봄), `unresolved`(봤는데 못 찾음, "연결 못 한 대상"이 세는 것), `bound` 세 상태다. `bound`는 후보 하나, 또는 코드가 하나로 정하지 못한 후보 여럿(이름만 맞은 대상, 오버로드, 동적 디스패치)이다. 후보가 여럿이면 모두 INFERRED여야 컴파일된다. 후보가 없는 `bound`도 컴파일되지 않는다.
  - import는 문장 하나가 위치 하나다. 모듈 대상(graphify `imports_from`)과 가져온 이름마다의 대상(graphify `imports`, 심볼을 가리킴)을 따로 묶는다. `export … from`은 `reexports` 목록에 둔다. 목록이 다르다는 것이 재수출 표시다. 전송 형식은 `imports`만 읽으므로, 파서가 재수출을 채워도 요청 바이트가 그대로다.
  - 참조 위치(`RefSite`)는 graphify의 ast 관계 이름을 그대로 쓴다: `calls`, `indirect_call`, `references`, `inherits`, `implements`, `dynamic_import`. 종류마다 허용하는 끝점과 `context`가 타입으로 정해진다. 예를 들어 `inherits`는 클래스 안에서만 적히고, 값으로 넘긴 함수(`indirect_call`)는 INFERRED만 된다. `contains`와 `method`는 심볼 트리에서 읽으므로 따로 저장하지 않는다. 관계 이름 전체는 `RelationKind` 하나다.
  - 출처는 `PROVENANCE_RULES` 표 하나에서 타입을 끌어내 허용 조합만 컴파일되게 한다. 출처는 후보마다 붙는다. 코드 지도에는 LLM 출처를 넣을 수 없다.
  - LLM이 만든 역할 사이 관계(`SemanticEdge`)에는 선택 필드 `evidence`를 둔다(T1-8이 채운다). EXTRACTED는 그 관계를 뒷받침하는 추출된 코드 관계를 하나 이상 가리켜야 하고 실선이다. INFERRED는 점선이고, 이름만 맞은 관계를 가리키거나 아무것도 가리키지 않는다. 가리키는 값(`RelationRef`)은 파일 경로, 줄, 관계 이름, 대상 파일, 신뢰도만 담는 JSON이다. 이 필드가 생기기 전에 캐시·공유된 레벨은 필드가 없을 뿐 그대로 읽힌다.
  - 전송 형식은 `toWireFile(wirePath, WireSource)`로만 만든다. `WireSource`는 심볼과 import 원문만 담는 타입이다. 그래서 나중 작업이 무엇을 채워도 요청 바이트가 그대로다.
  - 식별자 규칙은 둘이다.
    - `FilePath`는 astMap 키이고 `{root}/{저장소 기준 경로}` 모양이다. `root`는 고른 폴더 이름(로컬)이나 저장소 이름(GitHub)이며 `CodeMap.root`에 둔다. 저장소 기준 경로로 들어오는 입력, 곧 T1-6이 tsconfig `paths`나 워크스페이스로 찾은 경로와 T1-10이 읽는 graph.json `source_file`은 앞에 `root/`를 붙여야 `FilePath`가 된다. AI 요청에 쓰는 경로(`wirePath`)는 이 키와 따로 다룬다.
    - `SymbolId`의 `~n`(같은 파일에서 n번째로 나온 같은 이름)은 선언 순서에 따라 바뀐다. 함수 하나를 위로 옮기기만 해도 번호가 바뀐다. 그래서 `SymbolId`는 그 id를 만든 코드 지도 안에서만 쓴다. 캐시, 내보낸 파일, `RelationRef`처럼 저장하거나 세션을 넘는 값의 키로 쓰지 않는다. T1-10은 graphify 노드 id를 쓰지 않고 `contains` 트리에서 `SymbolId`를 다시 만든다. 그래서 같은 파일이라도 `~n`이 Ropeman 추출과 다를 수 있다.
- **기각 이유**: A는 첫 후속 작업에서 캐시와 예산을 깨고, 전송 형식이 곧 도메인 모델이 된다. B는 잘못된 출처 조합을 막지 못하고, 전송 형식의 바이트 유지가 어려워진다. B의 형식은 내보내기 형식으로만 쓴다(필요하면 코드 지도에서 만든다). C2는 위치 번호가 범위 안에 있는지, 해석이 끝났는데 관계가 없는 위치가 무엇인지를 실행 중에 따로 맞춰야 한다. graph.json에 없는 "적힌 이름"도 지어내야 한다. C3은 위치 id와 결과 표를 손으로 맞춰야 하고, 위치 종류와 결과 종류가 같은지 타입으로 묶이지 않는다. C4는 재수출이 `imports`에 들어가 전송 형식이 읽는 목록에 섞인다.
- **결과**: 같은 픽스처(파싱한 파일 51개, Markdown, 한글 이름, 중첩·중복 심볼, 예산 컷, 예산을 넘는 파일)의 전송 문자열 7종이 v2 이전과 바이트까지 같다. 키 순서를 바꾸거나, 빈 배지를 보내거나, 로컬 전용 종류를 보내는 변형은 모두 그 테스트에서 실패한다. 줄 범위를 보냈다면 심볼마다 `,"lines":[12,40]` 정도(16바이트)가 늘었을 것이다(추정, 측정 안 함). 타입 테스트는 잘못된 출처 조합, 후보 없는 `bound`, EXTRACTED가 섞인 여러 후보, 종류에 맞지 않는 끝점, 근거 없는 EXTRACTED 증거를 컴파일 오류로 확인한다. 후보 규칙을 느슨하게 바꾸면 그 테스트가 실패하는 것도 확인했다.
- **재검토 조건**: PASEO 비교 실험에서 호출이나 의존 관계를 AI가 보면 역할 판단이 뚜렷이 나아진다고 나오면, 전송 형식 v2를 따로 만들고 캐시 키 변경과 평가를 함께 한다. graph.json을 주 입력으로 정하면 파일 기록 대신 평면 그래프가 나은지 다시 본다. graphify에서 위치 하나에 EXTRACTED 대상이 여럿인 묶음(PASEO 호출 묶음 14,198개 중 299개가 대상 둘 이상)이 한 줄의 서로 다른 호출이 아니라 정말 한 호출의 후보로 확인되면, 후보 규칙을 다시 본다.
