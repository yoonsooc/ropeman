# ADR-21: 스켈레톤 v2는 브라우저에 두는 코드 지도로, AI 전송 형식은 v1에 고정

- **날짜**: 2026-11-12
- **문제**: 코드 지도에 줄 번호, 호출 관계, 파일로 연결된 import, 관계마다 출처(EXTRACTED/INFERRED)를 넣어야 한다. 그래야 사람과 에이전트가 관계마다 근거를 확인할 수 있다. 그런데 지금은 한 타입(`SkeletonFile`)이 파서 요약이면서 AI에 보내는 요청이다. 사실을 하나 더할 때마다 요청이 커진다. 250KB 예산에 PASEO는 이미 65~86개 파일만 들어간다. 분석 캐시 키는 요청 문자열의 SHA-256이라서, 요청이 1바이트만 달라져도 모든 사용자의 캐시가 무효가 된다.
- **검토 대안**:
  - (A) v1 전송 형식을 넓힌다. `SkeletonSymbol`에 `lines`, `SkeletonFile`에 `calls`와 `resolved`를 선택 필드로 두고, 비어 있으면 생략해 바이트를 유지한다. 지금 바꿀 양은 가장 적다. 하지만 T1-5가 호출을 채우는 순간 캐시 키가 모두 바뀌고 예산이 줄어든다. 출처를 둘 곳도 전송 필드밖에 없다.
  - (B) graphify처럼 평면 노드·관계 그래프로 바꾼다. T1-10 입력과 거의 1:1이다. 하지만 관계마다 `confidence`와 `source`를 따로 저장하면 "파서가 추론했다" 같은 잘못된 조합도 저장된다. 전송 형식을 만들려면 `contains` 관계에서 심볼 트리와 순서를 다시 짜야 해서 바이트 유지가 깨지기 쉽다. 파일 단위로 읽을 때마다 색인도 따로 필요하다.
  - (C) 파일마다 기록을 두는 코드 지도를 브라우저에만 두고, 전송 형식은 v1에서 투영한다. 관계는 그 관계가 적힌 파일의 기록에 둔다.
- **결정**: C. `types/codeMap.ts`에 `CodeMap`을 둔다. 파일 기록(`FileRecord`)은 심볼 트리(id, 모든 종류, 줄 범위), import 위치, 호출 위치를 갖는다. 대상은 `pending`, `file`/`symbol`/`external`(출처 포함), `unresolved` 네 상태다. 출처는 `PROVENANCE_RULES` 표 하나에서 타입을 끌어내 허용 조합만 컴파일되게 한다. 코드 지도에는 LLM 출처를 넣을 수 없다. 전송 형식은 `toWireFile(wirePath, WireSource)`로만 만든다. `WireSource`는 심볼과 import 원문만 담는 타입이다. 그래서 나중 작업이 무엇을 채워도 요청 바이트가 그대로다.
- **기각 이유**: A는 첫 후속 작업에서 캐시와 예산을 깨고, 전송 형식이 곧 도메인 모델이 된다. B는 잘못된 출처 조합을 막지 못하고, 전송 형식의 바이트 유지가 어려워진다. B의 형식은 내보내기 형식으로만 쓴다(필요하면 코드 지도에서 만든다).
- **결과**: 같은 픽스처(파싱한 파일 51개, Markdown, 한글 이름, 중첩·중복 심볼, 예산 컷, 예산을 넘는 파일)의 전송 문자열 7종이 v2 이전과 바이트까지 같다. 키 순서를 바꾸거나, 빈 배지를 보내거나, 로컬 전용 종류를 보내는 변형은 모두 그 테스트에서 실패한다. 줄 범위를 보냈다면 심볼마다 `,"lines":[12,40]` 정도(16바이트)가 늘었을 것이다(추정, 측정 안 함).
- **재검토 조건**: PASEO 비교 실험에서 호출이나 의존 관계를 AI가 보면 역할 판단이 뚜렷이 나아진다고 나오면, 전송 형식 v2를 따로 만들고 캐시 키 변경과 평가를 함께 한다. graph.json을 주 입력으로 정하면 파일 기록 대신 평면 그래프가 나은지 다시 본다.
