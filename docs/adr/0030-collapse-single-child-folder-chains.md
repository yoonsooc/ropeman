# ADR-30: 하위 폴더 하나만 가진 폴더 사슬은 노드 하나로 접는다

- **날짜**: 2026-11-17
- **문제**: 묶은 지도(`groupExtraction`)는 폴더마다 단계를 하나씩 만든다. Maven·Gradle 저장소(`pom.xml`, `src/main/scala/com/<조직>/<제품>/...`)는 갈라지는 폴더가 깊이 8~12에 있어서, `src`, `src/main`, `src/main/scala`, `src/main/scala/com` 단계가 저마다 노드 하나만 담는다. 사용자는 고를 것이 없는 단계를 예닐곱 번 드릴다운해야 의미 있는 그림을 보고, 에이전트와 일꾼은 그 단계에도 이름을 붙인다. Java, Kotlin, Go(`internal/pkg/...`), `packages/<이름>/src` 모노레포도 모양이 같다. 파일만 담은 폴더도 노드 하나(`files:<폴더>`)짜리 단계를 한 번 더 거쳐야 파일이 보였다. 무엇을 "부분 하나"로 볼지, 사슬을 어디까지 접을지, 접은 노드의 id와 제목을 무엇으로 할지, 이전 지도를 어떻게 읽을지 정해야 했다.
- **검토 대안**:
  - (A) 묶을 때 접는다. 하위 폴더 하나만 있고 직접 담은 파일이 없는 폴더는 단계를 만들지 않고, 사슬의 마지막 폴더를 노드로 쓴다. id는 마지막 폴더의 `dir:<경로>`, 제목은 단계 폴더에서 그 폴더까지의 경로다. 이전 `ropeman.json`은 적힌 그대로 읽는다.
  - (B) A와 같이 접되, 설정·문서 파일(`README.md`, `package.json`, YAML)만 직접 담은 폴더도 사슬로 본다. 루트의 `README.md` 때문에 사슬이 끊기지 않는다.
  - (C) 묶음은 그대로 두고 뷰어가 노드 하나짜리 단계를 건너뛴다. 이전 지도도 접혀 보이지만, 에이전트와 일꾼은 여전히 그 단계에 이름을 붙이고, 브리지 모드의 `node.expand`와 `ropeman.json`, `work.json`이 서로 다른 모양을 갖는다.
  - (D) 사슬 전체 경로로 새 id(`chain:src/main/scala/com/acme`)를 만든다. 접힌 노드가 다른 노드와 구분되지만, 이미 있는 `dir:` id와 그 id로 적은 `names.json` 항목이 바뀐다.
- **결정**: (A)를 골랐다.
  - 부분은 지금처럼 코드 지도에 파일이 있는 하위 폴더 하나하나와, 폴더에 직접 있는 파일 묶음 하나다. `pom.xml`처럼 Ropeman이 읽는 언어가 아닌 파일은 코드 지도에 없으므로 부분을 만들지 않는다. `README.md`, `package.json`, YAML처럼 지도에 들어가는 파일은 열 수 있는 파일이므로 부분 하나로 센다.
  - 하위 폴더가 하나이고 직접 담은 파일이 없는 폴더는 단계를 만들지 않는다. 그런 폴더가 이어지면 사슬 전체가 노드 하나다. 노드는 사슬의 마지막 폴더, 곧 파일을 직접 담거나 하위 폴더가 둘 이상인 첫 폴더다. 접는 깊이에 한도는 없다. 사슬 안의 폴더는 정보를 더하지 않고, 제목이 전체 경로를 담기 때문이다.
  - 노드 id는 마지막 폴더의 `dir:<경로>`다. 경로로 정해지므로 다시 추출해도 같고, 그 폴더를 이미 `dir:` id로 적은 `names.json` 항목이 그대로 맞는다. 사슬 안의 폴더 id(`dir:src`, `dir:src/main`)는 지도의 노드가 아니다. `node.expand`는 `unknown-node`로 답하고 `ropeman map`은 그 id의 이름을 `node-unknown`으로 돌려준다.
  - 제목은 단계 폴더에서 마지막 폴더까지의 경로(`main/scala/com/example/app`)다. 사슬이 없으면 지금처럼 폴더 이름 하나다. 설명은 다른 묶은 노드처럼 비워 둔다. 이름 붙이기 전에 문장을 지어 넣으면 이름처럼 읽힌다.
  - 루트도 같은 규칙으로 접는다. 루트가 하위 폴더 하나만 가지면 최상위 단계는 사슬이 끝나는 폴더의 단계다. `GroupedMap.topFolder`가 그 폴더이고 `work.json`의 최상위 `folder`에 들어간다.
  - 하위 폴더 없이 파일만 담은 폴더의 단계는 노드 하나(`files:<폴더>`)라서 만들지 않는다. 그 폴더의 `dir:` 노드가 바로 파일 단계(`fileLevel`)로 열리고, 파일이 하나면 노드는 그 파일을 연다. 최상위 단계만은 예외로 늘 폴더 단계다. 모든 파일이 한 폴더에 있는 저장소는 최상위가 `files:` 노드 하나다. 최상위를 파일 단계로 바꾸면 에이전트가 이름 붙일 1단계가 사라진다.
  - 규칙은 `packages/core/src/groupedMap.ts`의 `chainEnd` 한 곳에 있다. 폴더 단계를 만드는 곳은 `groupExtraction`뿐이고 `ropeman map`과 `ropeman serve`가 함께 쓴다. 브라우저의 `/`는 AI가 역할로 나누고 `/open`은 `ropeman.json`에 적힌 단계를 읽으므로, 앱에는 바꿀 폴더 단계 코드가 없다.
  - 이전 `ropeman.json`은 적힌 그대로 읽는다. 노드 하나짜리 단계도 올바른 트리라서 파서와 검증기를 통과한다. 스키마 버전은 1.2 그대로다. 필드가 늘지 않았기 때문이다.
- **기각 이유**:
  - (B) 루트의 `README.md`와 `package.json`은 사용자가 여는 파일이다. 사슬에 넣으면 파일이 접힌 노드 안에 숨는다. 루트에 파일이 있으면 최상위 단계에 부분이 둘 이상이라 고를 것이 있고, 사슬은 그 아래 `src/...` 노드에서 접힌다.
  - (C) 이름 붙이는 비용이 그대로다. 뷰어, `work.json`, `node.expand`가 서로 다른 트리를 보면 브레드크럼과 큐의 id가 어긋난다.
  - (D) 마지막 폴더의 `dir:` id만으로 노드가 하나로 정해져서 새 접두사가 필요 없다. 접두사를 늘리면 `ropeman.json` 읽는 쪽이 모두 새 형식을 알아야 한다.
- **결과**:
  - 정답 픽스처 `tests/fixtures/graphs/scala-deep`(`pom.xml`, `src/main/scala/com/example/app/{parse, store/memory, web/http}`)의 손으로 적은 단계(`scala-deep.levels.json`)와 묶은 지도가 같다. 루트가 `src/main/scala/com/example/app`까지 접힌다. 폴더 단계 14개 중 노드 하나짜리가 11개였는데 3개 중 0개가 됐다. 파일 단계 2개, 엣지 5개, 근거 5개는 그대로다.
  - `spring-petclinic`(`500158f`, 파일 37개)에 `ropeman map`을 돌린 결과: 폴더 단계 15개(노드 하나짜리 13개)가 2개(0개)가 됐다. 최상위의 `src` 카드에서 갈라지는 단계까지 7번 열던 것이 `src/main/java/org/springframework/samples/petclinic` 카드 한 번이다. 파일 37개, 엣지 9개, 근거 15개는 그대로이고 `ropeman verify`는 두 지도 모두 위반이 없다.
  - 기존 픽스처 6개 모두 최상위 아래에 노드 하나짜리 폴더 단계가 없다(`grouping.test.ts`). `ts-monorepo`의 최상위는 `apps/web`, `packages/core`, `shared`, `ts-monorepo/*`다.
  - 이전 bridge가 쓴 작업 폴더의 `names.json`을 새 bridge로 읽으면, 사슬 안 폴더의 id는 `node-unknown` 문제로 돌아온다. 에이전트가 `work.json`의 id로 다시 이름 붙이면 사라진다.
- **재검토 조건**:
  - 제목이 긴 사슬(깊이 10 이상)이 카드에서 읽히지 않는다는 보고가 나오면 앞부분을 줄이는 표시 규칙을 정한다. 지금은 카드 제목이 가운데를 줄인다(`utils/cardTitle.ts`).
  - 사용자가 사슬 안의 폴더(예: `src/main`)에 이름이나 설명을 달고 싶어 하면, 접힌 노드에 사슬의 폴더 목록을 필드로 싣는다(스키마 1.3).
  - 설정 파일만 담은 폴더 때문에 사슬이 끊겨 노드 하나짜리 단계가 다시 생긴다는 측정이 나오면 (B)를 다시 본다.
